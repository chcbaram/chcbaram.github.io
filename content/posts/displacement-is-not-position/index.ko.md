`wish-he` 는 시판 홀이펙트 키보드에 올리는 커스텀 펌웨어다. HPM5361(RISC-V, 400 MHz)
에서 돈다. 홀이펙트 키는 눌림/떼짐이 아니라 깊이를 보고하므로, 래피드 트리거가 행정 위의
고정된 지점이 아니라 **방향이 얼마나 되돌았는지** 로 판정할 수 있다.

이 글은 그 계층을 만들면서 잘못 내렸다가 뒤집은 판단들에 대한 것이다. 가장 큰 것은
이거다. **재입력 거리는 이동량인데 나는 그것을 위치처럼 저장하고 있었다.** 카운트와
밀리미터가 직선으로 이어져 있는 동안에는 아무도 알아챌 수 없었다. 그 관계가 직선이
아니게 된 순간, 손가락이 실제로 머무는 깊이에서 래피드 트리거가 두 배로 예민해졌다.

## 설정은 전부 키별이고, "전역" 은 전체 선택일 뿐이다

이게 들어가기 전에는 판정이 전역 상수를 읽고 있었다. 설정 도구의 입력지점 슬라이더는
EEPROM 에 쓰고 있었고 판정에는 닿지도 않았다. 양쪽 다 따로 보면 멀쩡해 보였다.

그래서 설정 기록을 키웠다. 키별 설정 구조체가 8바이트에서 24바이트로, 저장 기록이
544 B 에서 1568 B 가 됐다. 키마다 입력지점, 해제지점, RT 재입력, RT 입력 해제, 바닥 보호,
데드존, RT 플래그를 들고 있다.

`firmware/wish-he/src/hw/driver/keys.c`
([퍼머링크](https://github.com/chcbaram/wish-he/blob/2d5083019c522b35f0fe0d7c4f6d8df51b99d22f/firmware/wish-he/src/hw/driver/keys.c#L697-L708))

```c
typedef struct
{
  uint16_t press_um;       /* 입력지점        0.01mm */
  uint16_t release_um;     /* 해제지점        0.01mm */
  uint16_t rt_press_um;    /* RT 재입력       0.01mm */
  uint16_t rt_release_um;  /* RT 입력 해제    0.01mm */
  uint16_t bottom_um;      /* 바닥 보호       0.01mm */
  uint16_t dead_um;        /* 데드존          0.01mm */

  uint8_t  sw_type;        /* 스위치 종류 인덱스 */
  uint8_t  rt_flags;       /* KEYS_RT_* */
```

정착한 규칙은 **판정이 언제나 키별 값을 읽는다** 는 것이다. 어느 키를 설정할지 고르는
화면에서는 "전체 선택" 이 이미 전역 설정이다. 거기에 전역이라는 개념을 하나 더 두면
"둘 중 뭐가 이기나" 라는 질문이 영영 따라다닌다. 프로파일의 전역 필드가 하는 일은 둘뿐이다.
새 설정을 만들 때의 기본값, 그리고 설정 도구가 전역으로 쓸 때 64키에 뿌리는 값.

설정은 0.01 mm 로 들어오고 판정은 카운트로 돈다. 바꾸려면 키별 전 행정이 필요한데 그건
나눗셈이고, 64칸을 35 kHz 로 도는 루프에 나눗셈을 넣을 자리가 없다. 그래서 문턱 표를
미리 구워 두고 설정이나 보정이 바뀔 때만 다시 만든다.

### 전 행정이 4.0 mm 라고 돼 있었고 스위치는 3.4 mm 였다

스위치 표의 기본 전 행정이 4.0 mm 였다. 이 보드의 스위치는 3.4 mm 를 간다. 카운트로 하는
판정은 신경도 안 썼지만, 화면에 뜨는 밀리미터는 전부 18 % 어긋나 있었다. "입력지점
1.00 mm" 가 실은 0.85 mm 였다.

증거는 첫날부터 화면에 있었다. 키를 바닥까지 누르면 3.385 mm 로 읽혔다. 나는 그걸
"4.0 mm 스위치를 3.385 mm 까지 눌렀다" 로 읽었다. 실은 3.4 mm 스위치를 끝까지 누른
것이었다. 그 잘못된 독해 위에 분석을 두 번이나 더 쌓았고, 거기에는 나중에 지워야 했던
"두 눈금이 4 % 안에서 일치한다" 는 결론도 들어 있었다.

지금 스위치 표는 두 종류다. "이게 뭔지는 모르지만 전 행정은 대충 맞다" 용 범용 항목, 그리고
데이터시트 전 행정을 쓰는 제품 항목. **카운트로 된** 전 행정은 어느 데이터시트에도 없다.
자석 세기와 센서 위치가 정하는 값이라 보드에서 재야 한다.

## 바닥 보호와 데드존은 다른 물건이다

둘 다 판정을 멈추는 구간이라 같은 얘기처럼 읽힌다. 행정의 반대쪽 끝에 있고 서로 무관한
문제를 푼다.

| | 어디 | 하는 일 |
|---|---|---|
| 데드존 | 위쪽, 쉬는 자리 근처 | 진동과 공차로 생기는 오입력을 무시한다 |
| 바닥 보호 | 아래쪽, 바닥 근처 | RT 의 입력 해제를 끈다 |

바닥 보호가 있는 이유는 RT 입력 해제가 "도달한 가장 깊은 지점에서 얼마나 올라왔나" 로
걸리기 때문이다. 키를 바닥에 대고 누르고 있으면 그 기준점이 바닥에 박히는데, 손가락은
누르고 있는 동안에도 0.1~0.3 mm 씩 힘이 풀린다. 그 풀림만으로 해제가 걸려서 키가 덜덜
떨린다. 일반 모드에서는 해제지점이 바닥에서 한참 떨어진 절대 위치라 이런 일이 없다. RT
에만 있는 문제다. 잡음 문제도 아니다. 0.1 mm 가 63 카운트인데 잡음 시그마는 7 쯤이다.
데드존 기본값은 0 이고, 진짜로 진동이 있는 자리에서만 사용자가 올린다.

## 재입력 거리는 위치가 아니라 이동량이다

그다음에 카운트-밀리미터 직선 매핑을 스위치의 실제 자속-거리 곡선으로 바꿨다. 그건 그
자체로 [다른 글](../flux-to-distance-curve/) 이다. 여기서 중요한 건 그게 무엇을 깼는가다.

절대 위치 — 입력지점, 해제지점, 데드존, 바닥 보호 — 는 곡선에 통과시키기만 하면 제대로
나온다. RT 의 두 값은 위치가 아니다. **이동량** 이고, 곡선 위에서는 같은 밀리미터가 어디서
움직였느냐에 따라 카운트가 완전히 달라진다. 나는 그 둘을 키마다 카운트 하나로 들고
있었다. 그러니 각각 정확히 한 깊이에서만 맞았다.

![RT 재입력을 0.50 mm 로 둔 경우. 카운트 문턱 하나로 들고 있으면 한 깊이에서만 0.50 mm 였고, 깊이 구역마다 문턱을 구워 두면 어디서나 0.50 mm 다](rt-displacement.svg)

깊은 쪽이 타이핑할 때 손가락이 머무는 자리다. 래피드 트리거를 켜면 내가 적어 넣은
숫자보다 훨씬 신경질적으로 느껴졌던 이유가 그거였다.

매 표본마다 역변환하는 게 정직한 해법인데 64칸 35 kHz 에서는 감당이 안 된다. 그래서 문턱을
구워 둔다. 정규화한 깊이의 상위 3비트로 여덟 구역을 잡고, 다시 만들 때 구역마다 문턱을
계산한다. 스캔 루프가 하는 일은 곱셈 하나와 시프트 하나다.

`firmware/wish-he/src/hw/driver/keys.c`
([퍼머링크](https://github.com/chcbaram/wish-he/blob/2d5083019c522b35f0fe0d7c4f6d8df51b99d22f/firmware/wish-he/src/hw/driver/keys.c#L2515-L2521))

```c
ATTR_RAMFUNC static inline uint32_t keysRtZone(uint32_t idx, uint16_t cnt)
{
  uint32_t z = ((uint32_t)cnt * stroke_recip[idx])
               >> (KEYS_STROKE_RECIP_SH + 15 - KEYS_RT_ZONE_BITS);

  return (z >= KEYS_RT_ZONE_CNT) ? (KEYS_RT_ZONE_CNT - 1) : z;
}
```

키당 32바이트, 보드 전체로 2 KB 든다. 그리고 RT 를 켠 채로 스캔이 28 us 로 나왔다. 안
켰을 때와 같다.

고치는 안에서 또 두 가지를 틀렸다.

**구역은 지금 깊이가 아니라 기준점(peak) 에서 고른다.** 되돌림은 그 기준점에서 시작하는
이동이니, 문턱도 **그 자리의** 기울기로 재야 맞다.

**바닥 구역은 뒤에서 재야 한다.** 재입력 문턱은 구역 가운데에서 아래쪽으로 거리를 더해서
만든다. 가장 깊은 구역에서는 그게 행정 끝을 넘어가 잘리는데, 잘린 문턱은 오히려 **작게**
나온다. 481 카운트가 160 이 된다. 그러면 재입력이 바닥에서 제일 쉽게 걸린다. 이 변경이
노리던 것과 정반대다.

`firmware/wish-he/src/hw/driver/keys.c`
([퍼머링크](https://github.com/chcbaram/wish-he/blob/2d5083019c522b35f0fe0d7c4f6d8df51b99d22f/firmware/wish-he/src/hw/driver/keys.c#L2343-L2354))

```c
      dn = m0 + k->rt_press_um;
      if (dn > travel)
      {
        uint32_t lo = (travel > k->rt_press_um) ? (travel - k->rt_press_um) : 0;

        t->rt_press[z] = (uint16_t)(((KEYS_CURVE_ONE - Z_U(lo)) * stroke)
                                    / KEYS_CURVE_ONE);
      }
      else
      {
        t->rt_press[z] = (uint16_t)(((Z_U(dn) - u0) * stroke) / KEYS_CURVE_ONE);
      }
```

바닥에서 거꾸로 재면 마지막 구간의 기울기가 나온다. "여기서 0.30 mm 는 몇 카운트인가" 의
올바른 답이다. 그리고 키가 그보다 더 내려갈 수 없으니, 바닥에 대고 누르고 있는 동안에는
재입력이 아예 안 걸린다. 내가 원하던 동작이다.

이 잘림을 본 건 `keys rt` 가 여덟 구역을 다 찍기 때문이다. 대표값 하나만 찍었으면 묻혔다.

![`keys rt` 는 설정 하나 뒤에 있는 문턱 여덟 개를 다 찍는다. 재입력 0.50 mm 가 행정을 따라 175 에서 718 카운트가 되고, 마지막 둘이 같다 — 바닥 구역이 행정을 다 쓴 것이다](keys-rt-w400.png)

## 없는 문제를 고치지 않기

드리프트 보정은 512 ms 마다 키마다 기준값을 한 걸음 움직인다. 내 메모에는 이 일을 나눠
퍼뜨려야 한다고 적혀 있었다. 64키를 한 스캔에서 다 하면 그 스캔이 무거워지고 주기가
흔들린다는 이유였다.

건드리기 전에 쟀다. 드리프트를 **매 스캔** 돌려 봤더니 `keysUpdate` 가 28 us, 늘 같은
값이었다. 64칸에 비교 몇 번과 증가 몇 번은 드러나지도 않는다. 카운터가 반대쪽에서도 같은
말을 했다. 45초 동안 60 us 를 넘은 스캔이 30번인데 드리프트는 88번 돌았다. 둘이 안
겹친다.

진짜 문제는 걸음 크기였다. 표본 셋을 누적하면서 눈금이 세 배가 됐는데 걸음은 1 카운트로
그대로였다. 그러니 한 걸음이 행정의 1/836 에서 1/2508 로 줄었다. 온도 드리프트를 따라가는
속도가 세 배 느려진 것이다. 온도는 세 배 느려지지 않았다. 걸음을 누적 개수에 묶으니
물리적인 속도가 돌아왔다.

같은 주에 `keyboard_task max 308 us` 를 보고 구조를 한참 의심한 적도 있다. 초과 횟수를
세니 1분 만에 끝났다. 153만 번 중 3번, 전부 부팅과 CLI 중이었다. 최대값은 세 번과 오천
번을 구별해 주지 않는다.

## 그 주에 배운 것

여기서 틀린 것은 전부 **재기 전에 움직여서** 틀렸다.

| 짐작 | 실측 |
|---|---|
| 드리프트가 스캔 주기를 흔든다 | 어느 쪽이든 28 us |
| `max 308 us` 는 구조 문제다 | 153만 번 중 3번, 부팅 때 |
| 전 행정은 4.0 mm | 3.4 mm |
| 재입력 거리는 숫자 하나 | 깊이 구역마다 하나씩 |

고치지 않기로 하는 것도 결과다. 재는 일이 먼저였다면.

## 아직 남은 것

- 재입력 거리와 입력 해제 거리를 실제로 쓰면서 맞춰 가는 것. 이제는 숫자 하나를 찾는
  일이다. 구역 작업 전에는 질문 자체가 성립하지 않았다. 키가 깊이마다 다르게 굴었으니까.
- 스위치 표를 장치에서 읽어 오는 것. 지금은 펌웨어와 웹앱이 각각 사본을 들고 있어서
  갈라질 수 있다.
- 여덟 구역은 고른 값이다. 몇 가지 크기를 놓고 보다가 적당해 보이는 데서 정했다. 넷이나
  열여섯과 하드웨어에서 견준 기록은 저장소에 없다. 판단으로 정한 것을 측정 결과인 양
  적지는 않겠다.
